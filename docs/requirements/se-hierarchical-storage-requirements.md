# Requirements: Иерархическая структура хранения файлов в SE

## Метаданные

- **Дата**: 2026-03-01
- **Статус**: Approved (brainstorm)
- **Связанный план**: `plans/se-stateless-refactoring-plan.md` → Phase 5.5
- **Область**: Storage Element — файловое хранилище

---

## Контекст и мотивация

### Текущая структура (плоская)

В новом Go-проекте SE все файлы хранятся в одном каталоге (`SE_DATA_DIR`):

```
/data/
├── photo_admin_20260221150405_a1b2c3d4.jpg
├── photo_admin_20260221150405_a1b2c3d4.jpg.attr.json
├── document_user_20260220094530_f5e6d7c8.pdf
├── document_user_20260220094530_f5e6d7c8.pdf.attr.json
├── mode.json
└── .locks/
    └── {fileID}.lock
```

`StoragePath` в attr.json содержит только имя файла: `photo_admin_20260221150405_a1b2c3d4.jpg`.

### Старый проект (Python, иерархическая структура)

В `old_artstore/` файлы хранились с date-based иерархией:

```
/data/
└── 2025/
    └── 01/
        └── 10/
            └── 15/
                ├── report_ivanov_20250110T153045_a1b2c3d4.pdf
                └── report_ivanov_20250110T153045_a1b2c3d4.pdf.attr.json
```

Формат пути: `{year}/{month}/{day}/{hour}/`. Attr-файлы хранились рядом с основными файлами.

### Проблемы плоской структуры

1. **Масштабируемость FS**: ext4 деградирует при >100K файлов в одном каталоге.
   XFS лучше, но тоже имеет ограничения.
2. **Администрирование**: Невозможно визуально ориентироваться — лента тысяч файлов
   без группировки. Администратор не может быстро найти файлы за конкретную дату.
3. **Reconcile/GC**: `os.ReadDir()` на одном каталоге с 500K файлов — одна дорогая
   операция вместо инкрементального обхода по датам.
4. **S3 готовность**: S3 `ListObjectsV2` с flat namespace менее эффективен, чем
   с prefix-based структурой (delimiter `/` позволяет виртуальные папки и
   инкрементальный листинг).
5. **Несовместимость с планом Phase 7**: Структура S3 bucket в Phase 7 не учитывает
   date-based иерархию, что противоречит требованиям администрирования.

## Функциональные требования

### FR-1: Иерархическая структура каталогов

**Описание**: При загрузке файла SE создаёт каталог на основе даты загрузки и
сохраняет файл в этот каталог.

**Формат пути**: `{year}/{month}/{day}/{filename}`

**Пример**:
```
/data/
├── 2026/
│   ├── 02/
│   │   ├── 20/
│   │   │   ├── document_user_20260220094530_f5e6d7c8.pdf
│   │   │   └── document_user_20260220094530_f5e6d7c8.pdf.attr.json
│   │   └── 21/
│   │       ├── photo_admin_20260221150405_a1b2c3d4.jpg
│   │       └── photo_admin_20260221150405_a1b2c3d4.jpg.attr.json
│   └── 03/
│       └── 01/
│           ├── report_viewer_20260301120000_deadbeef.pdf
│           └── report_viewer_20260301120000_deadbeef.pdf.attr.json
├── mode.json
└── .locks/
    └── {fileID}.lock
```

**Правила**:
- Дата берётся из `time.Now().UTC()` на момент загрузки
- Каталоги создаются автоматически (`os.MkdirAll`) при первой записи
- Формат компонентов: `YYYY` (4 цифры), `MM` (2 цифры с ведущим нулём), `DD` (2 цифры)
- Go time layout: `"2006/01/02"` (для `time.Format()`)

### FR-2: Обновлённый StoragePath

**Описание**: `StoragePath` в attr.json и in-memory index содержит полный относительный
путь от `SE_DATA_DIR` до файла.

**Было**: `photo_admin_20260221150405_a1b2c3d4.jpg`
**Стало**: `2026/02/21/photo_admin_20260221150405_a1b2c3d4.jpg`

**Влияние**:
- `FileMetadata.StoragePath` меняет формат
- API-ответы `GET /api/v1/files/{fileId}` возвращают новый формат StoragePath
- `FullPath()` = `filepath.Join(dataDir, storagePath)` — формула не меняется
- attr.json рядом с файлом: `{storagePath}.attr.json` — формула не меняется

### FR-3: Attr-файлы рядом с основными файлами

**Описание**: Attr-файлы (`*.attr.json`) хранятся в том же каталоге, что и основные
файлы. Это удобно для администрирования — при просмотре файловой системы видны пары
файл + метаданные.

**Пример**:
```
2026/02/21/
├── photo_admin_20260221150405_a1b2c3d4.jpg         ← data
└── photo_admin_20260221150405_a1b2c3d4.jpg.attr.json  ← metadata
```

Это поведение уже реализовано и не требует изменений.

### FR-4: Рекурсивный обход для Index/GC/Reconcile

**Описание**: Все операции сканирования файлов должны использовать рекурсивный обход
(`filepath.WalkDir`) вместо `os.ReadDir` по одному каталогу.

**Затронутые компоненты**:
- `index.BuildFromDir()` — построение in-memory индекса при старте
- `attr.ScanDir()` — сканирование всех attr.json (если есть)
- `reconcile` service — поиск orphaned файлов и attr.json
- `gc` service — если он напрямую сканирует FS

**Требования к WalkDir**:
- Пропускать скрытые каталоги (`.locks/`, `.meta/` и т.д.)
- Пропускать `mode.json` в корне
- Корректно обрабатывать символические ссылки (или игнорировать)
- Не следовать за symlink-ами в каталоги (предотвращение циклов)

### FR-5: Единая структура для S3

**Описание**: Phase 6 и Phase 7 должны учитывать, что StoragePath уже содержит
date-based иерархию. S3 key формируется как:

```
{storageID}/data/{storagePath}
```

**Пример S3 key**: `se-edit-1/data/2026/02/21/photo_admin_20260221150405_a1b2c3d4.jpg`
**Attr S3 key**: `se-edit-1/data/2026/02/21/photo_admin_20260221150405_a1b2c3d4.jpg.attr.json`

Это позволяет:
- S3 `ListObjectsV2` с `Prefix=se-edit-1/data/2026/02/21/` для листинга по дате
- Консистентный admin experience между LocalFS и S3

### FR-6: Обновление OpenAPI спецификации

**Описание**: Обновить описание `storage_path` в OpenAPI спецификации SE для
отражения нового формата.

**Изменения**:
- `FileMetadataResponse.storage_path`: добавить description с примером нового формата
- `FileUploadResponse.storage_path`: аналогично
- Обновить example значения

### FR-7: Lock-файлы остаются плоскими

**Описание**: Структура lock-файлов не меняется:

```
{dataDir}/.locks/{fileID}.lock
```

Lock-файлы не связаны со структурой каталогов данных. FileID (UUID v4) уникален,
коллизий нет. Lock-и короткоживущие (TTL 120s), их количество ограничено текущими
upload-ами.

### FR-8: mode.json остаётся в корне

**Описание**: `mode.json` остаётся в `{dataDir}/mode.json`. Это метаданные всего
Storage Element, не конкретного файла.

При рекурсивном обходе `filepath.WalkDir` файл `mode.json` в корне должен
пропускаться (он не является data-файлом и не является attr.json).

## Нефункциональные требования

### NFR-1: Производительность сканирования

`filepath.WalkDir` по иерархической структуре не должен быть медленнее, чем
`os.ReadDir` по плоской структуре на том же объёме файлов. На практике WalkDir
на иерархии быстрее, так как каталоги содержат меньше записей.

### NFR-2: Создание каталогов

`os.MkdirAll` при каждом upload — допустимые накладные расходы. При существующем
каталоге операция — no-op.

### NFR-3: Совместимость с NFS

Иерархическая структура должна корректно работать на NFS v4 (shared PVC в K8s).
`os.MkdirAll` на NFS — атомарная операция.

## Влияние на другие компоненты

### Admin Module

AM хранит `storage_path` в PostgreSQL (таблица `files`). Формат значения изменится:
- **Было**: `photo_admin_20260221150405_a1b2c3d4.jpg`
- **Стало**: `2026/02/21/photo_admin_20260221150405_a1b2c3d4.jpg`

AM не интерпретирует `storage_path` — использует как opaque string для передачи
клиентам. **Изменения в AM не требуются.**

### Ingester Module

IM получает `storage_path` от SE в ответе на upload и передаёт в AM для регистрации.
IM не интерпретирует `storage_path`. **Изменения в IM не требуются.**

### Query Module

QM получает `storage_path` из AM и передаёт в SE для download.
QM не интерпретирует `storage_path`. **Изменения в QM не требуются.**

### Интеграционные тесты

Тесты SE проверяют `storage_path` в ответах API. Необходимо обновить assertions,
если они проверяют конкретный формат StoragePath.

## User Stories / Acceptance Criteria

### US-1: Загрузка файла

**Как** пользователь, **я хочу** загрузить файл в SE, **чтобы** он сохранился в
иерархической структуре каталогов по дате.

**Критерии приёмки**:
- Файл сохранён в `{dataDir}/YYYY/MM/DD/{storageName}`
- Attr.json сохранён рядом: `{dataDir}/YYYY/MM/DD/{storageName}.attr.json`
- StoragePath в attr.json и API-ответе: `YYYY/MM/DD/{storageName}`
- Каталог создан автоматически, если не существовал

### US-2: Скачивание файла

**Как** клиент, **я хочу** скачать файл по fileId, **чтобы** SE нашёл его в
иерархической структуре.

**Критерии приёмки**:
- SE находит файл по StoragePath из in-memory index
- `FullPath()` корректно разрешает путь
- Файл отдаётся через `http.ServeContent`

### US-3: Reconcile

**Как** SE, **я хочу** просканировать все файлы для reconciliation, **чтобы**
обнаружить orphaned файлы и attr.json.

**Критерии приёмки**:
- `filepath.WalkDir` рекурсивно обходит `{dataDir}/YYYY/MM/DD/`
- Пропускает `.locks/`, `mode.json` и прочие служебные файлы
- Находит orphaned data-файлы (без attr.json)
- Находит orphaned attr.json (без data-файла)

### US-4: Администрирование через FS

**Как** администратор, **я хочу** просматривать файловую систему SE (NFS или S3),
**чтобы** видеть файлы, организованные по датам, с метаданными рядом.

**Критерии приёмки**:
- `ls /data/2026/02/21/` показывает файлы и attr.json за 21 февраля
- Структура одинакова для LocalFS и S3 (S3 console, aws cli)

## Открытые вопросы

1. **Пустые каталоги**: Если все файлы за день удалены (GC), нужно ли удалять
   пустые каталоги `YYYY/MM/DD/`? Или оставить как есть?
   - Рекомендация: не удалять. Пустые каталоги занимают ~4KB (inode) и не мешают.
     Удаление каталогов — дополнительная логика с race conditions.

2. **Часовой пояс**: Дата берётся из `time.Now().UTC()` — т.е. каталоги организованы
   по UTC. Администратор в другом часовом поясе может быть удивлён.
   - Рекомендация: UTC — стандарт для серверов. Документировать это.
