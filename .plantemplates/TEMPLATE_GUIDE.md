# 📖 Руководство по использованию Development Plan Template

## Введение

Этот шаблон предназначен для создания стандартизированных планов разработки, которые могут использоваться как AI-ассистентами для пошаговой реализации, так и разработчиками для отслеживания прогресса.

## 🎯 Цели шаблона

1. **AI-совместимость**: AI-ассистент может возобновить работу после перерыва
2. **Отслеживание прогресса**: Визуальное представление статуса проекта
3. **Управление зависимостями**: Явные зависимости между фазами и подпунктами
4. **Критерии завершения**: Четкие чеклисты для определения "готовности"
5. **Версионирование**: Отслеживание изменений структуры плана

## 🚀 Быстрый старт

### 1. Скопируйте шаблон

```bash
cp DEVELOPMENT_PLAN_TEMPLATE.md DEVELOPMENT_PLAN.md
```

### 2. Заполните метаданные

```markdown
## 📋 Метаданные

- **Версия плана**: 1.0.0
- **Дата создания**: 2026-02-10
- **Последнее обновление**: 2026-02-10
- **Статус**: Pending
```

### 3. Создайте фазы

Определите основные фазы вашего проекта:
- Инфраструктура
- Core функциональность
- Интеграция
- Тестирование
- Deployment
- Documentation
- Commit

### 4. Разбейте фазы на подпункты

Каждый подпункт должен:
- Быть логически завершенным
- Укладываться в контекст AI (одна сессия работы)
- Иметь четкие входы и выходы (артефакты)

### 5. Удалите комментарии

Перед началом работы удалите все инструкции в `<!-- -->`.

## 📚 Структура плана

### Метаданные

Основная информация о плане:
- **Версия**: Семантическое версионирование (major.minor.patch)
- **Даты**: Создание и последнее обновление
- **Статус**: Pending → In Progress → Completed

### История версий

Отслеживание структурных изменений плана:

```markdown
- **v2.1.0** (2026-02-10): Добавлена Phase 5 (Monitoring)
- **v2.0.0** (2026-02-05): Реструктурирована Phase 3
- **v1.0.0** (2026-02-01): Начальная версия
```

**Когда создавать новую версию:**
- ➕ Добавление/удаление фазы
- ➕ Добавление/удаление подпункта
- ➕ Изменение зависимостей
- ❌ Простое обновление статуса (чекбоксы)
- ❌ Исправление опечаток

### Текущий статус

**Критически важная секция для AI!**

```markdown
## 📍 Текущий статус

- **Активная фаза**: Phase 3
- **Активный подпункт**: 3.2
- **Последнее обновление**: 2026-02-10 14:30
- **Примечание**: API endpoints готовы, начинаем тестирование
```

AI использует эту секцию для определения точки возобновления работы.

**Обновляйте при:**
- Переходе к новому подпункту
- Завершении подпункта
- Переходе к новой фазе
- Возникновении важного контекста

### Оглавление

Навигация и быстрый обзор прогресса:

```markdown
- [x] [Phase 1: Setup](#phase-1-setup)
- [ ] [Phase 2: Implementation](#phase-2-implementation)
```

**Особенности:**
- Чекбоксы отражают статус фазы (полностью завершена или нет)
- Якорные ссылки ведут к соответствующей фазе
- Автоматически генерируются якоря из заголовков (lowercase, дефисы)

## 🔧 Работа с фазами

### Структура фазы

```markdown
## Phase N: Название фазы

**Dependencies**: Phase X, Phase Y (или None)
**Status**: Pending / In Progress / Completed

### Описание
[Что достигается в этой фазе]

### Подпункты
[Список подпунктов]

### ✅ Критерии завершения Phase N
[Чеклист]
```

### Зависимости фаз

**Фазы выполняются СТРОГО ПОСЛЕДОВАТЕЛЬНО**

```markdown
## Phase 1: Setup
**Dependencies**: None

## Phase 2: Implementation
**Dependencies**: Phase 1  ← Нельзя начать до завершения Phase 1

## Phase 3: Testing
**Dependencies**: Phase 1, Phase 2  ← Требует обе предыдущие фазы
```

### Статусы фаз

- **Pending**: Еще не начата
- **In Progress**: В процессе выполнения
- **Completed**: Все подпункты и критерии выполнены

### Критерии завершения

**Обязательные критерии:**
```markdown
- [ ] Все подпункты завершены (X.1, X.2, ...)
```

**Для фаз с контейнерами/приложениями:**
```markdown
- [ ] **Контейнер успешно собран**
- [ ] **Все тесты пройдены**
```

**Специфичные критерии:**
```markdown
- [ ] API документация обновлена
- [ ] Code review пройден
- [ ] Performance benchmarks в норме
```

## 🎯 Работа с подпунктами

### Структура подпункта

```markdown
- [ ] **X.Y Название подпункта**
  - **Dependencies**: X.Z (или None)
  - **Description**: Детальное описание задачи
  - **Creates**:
    - `file1.go`
    - `file2.yaml`
  - **Edited**
    - `file1.go`
    - `file2.yaml`
  - **Links**:
    - [Library Docs](https://example.com)
```

### Зависимости подпунктов

**Подпункты МОГУТ выполняться ПАРАЛЛЕЛЬНО**

```markdown
- [ ] **2.1 Frontend component**
  - **Dependencies**: None

- [ ] **2.2 Backend API**
  - **Dependencies**: None
  ← 2.1 и 2.2 могут выполняться параллельно

- [ ] **2.3 Integration**
  - **Dependencies**: 2.1, 2.2
  ← 2.3 требует завершения 2.1 и 2.2
```

### Артефакты (Creates)

**Явно указывайте что создается:**

```markdown
**Creates**:
  - `Dockerfile` ← файл
  - `internal/api/handler.go` ← код
  - Docker image ← артефакт сборки
  - Database migration v001 ← миграция
  - API documentation ← документация
```

**Зачем это нужно:**
- AI понимает ожидаемый результат
- Легко проверить выполнение
- Документирование outputs

### Ссылки (Links)

**Только на существующие ресурсы:**

✅ **Правильно:**
```markdown
**Links**:
  - [Go Docker Image](https://hub.docker.com/_/golang)
  - [Chi Router Docs](https://github.com/go-chi/chi)
  - [internal/config/config.go](./internal/config/config.go)
```

❌ **Неправильно:**
```markdown
**Links**:
  - [будущий файл handler.go]  ← Файл еще не существует
  - internal/api/  ← Не ссылка
```

### Размер подпункта

**Правило "одна AI сессия":**

✅ **Хороший размер:**
- Создать Dockerfile с multi-stage build
- Реализовать CRUD API для одной сущности
- Написать интеграционные тесты для модуля
- Настроить CI/CD pipeline

❌ **Слишком большой:**
- Реализовать весь backend API (разбить на подпункты)
- Создать полный frontend (разбить на компоненты)

❌ **Слишком маленький:**
- Добавить одну строку в конфиг
- Исправить опечатку
- Обновить import

## 🔄 Workflow использования

### Для AI-ассистента

1. **Начало работы**
   - Прочитать "Текущий статус"
   - Найти активный подпункт
   - Проверить зависимости

2. **Выполнение подпункта**
   - Прочитать Description
   - Проверить Creates (что нужно создать)
   - Изучить Links (документацию)
   - Выполнить работу
   - Создать указанные артефакты

3. **Завершение подпункта**
   - Отметить чекбокс `- [x]`
   - Обновить "Текущий статус"
   - Проверить, можно ли начать следующий подпункт (зависимости)

4. **Завершение фазы**
   - Проверить все чекбоксы в "Критерии завершения"
   - Отметить фазу в Оглавлении `- [x]`
   - Обновить Status фазы на "Completed"

### Для разработчика

1. **Мониторинг прогресса**
   - Смотреть Оглавление для общей картины
   - Проверять "Текущий статус" для деталей

2. **Планирование работы**
   - Выбрать подпункты без зависимостей
   - Проверить Creates для понимания scope
   - Изучить Links для подготовки

3. **Изменение плана**
   - При добавлении фазы/подпункта → новая версия
   - Обновить "История версий"
   - Обновить метаданные (дата, версия)

## 💡 Best Practices

### ✅ Рекомендуется

1. **Явность везде**
   - Всегда указывайте Dependencies (даже None)
   - Всегда указывайте Creates (что создается)
   - Всегда обновляйте "Текущий статус"

2. **Логическая группировка**
   - Группируйте связанные задачи в одну фазу
   - Фаза = законченный этап (setup, implementation, testing, deployment)

3. **Размер имеет значение**
   - Фаза: 2-6 подпунктов
   - Подпункт: 1-2 часа работы AI
   - План: 3-7 фаз

4. **Тестирование**
   - Если фаза собирает что-то исполняемое → обязательно тестирование
   - Тесты могут быть отдельным подпунктом или фазой

5. **Версионирование**
   - Semver: major.minor.patch
   - Major: удаление фазы, кардинальная реструктуризация
   - Minor: добавление фазы/подпункта
   - Patch: изменение описаний, зависимостей

### ❌ Избегайте

1. **Неявных зависимостей**
   ```markdown
   ❌ Dependencies:  ← Пусто, но зависимость есть
   ✅ Dependencies: None  ← Явно указано
   ```

2. **Слишком большие подпункты**
   ```markdown
   ❌ 2.1 Реализовать весь backend
   ✅ 2.1 API routing
   ✅ 2.2 Database layer
   ✅ 2.3 Business logic
   ```

3. **Ссылки на несуществующий код**
   ```markdown
   ❌ Links: [future-handler.go]
   ✅ Links: [Chi Router Docs](https://github.com/go-chi/chi)
   ```

4. **Забытый "Текущий статус"**
   - AI не поймет, где продолжить работу
   - ВСЕГДА обновляйте при переходе между подпунктами

5. **Нечеткие критерии завершения**
   ```markdown
   ❌ - [ ] Все работает
   ✅ - [ ] Все тесты проходят (coverage > 80%)
   ✅ - [ ] API отвечает корректными HTTP статусами
   ```

## 🔧 Troubleshooting

### AI не может продолжить работу

**Проблема**: AI спрашивает "с чего начать?"

**Решение**:
1. Проверьте "Текущий статус" - указан ли активный подпункт?
2. Проверьте зависимости - все ли выполнены?
3. Обновите timestamp в "Последнее обновление"

### План стал слишком большим

**Проблема**: План не помещается в контекст AI

**Решение**:
1. Разбейте на несколько планов (по модулям)
2. Архивируйте завершенные фазы в отдельный файл
3. Создайте мета-план со ссылками на детальные планы

### Изменились требования

**Проблема**: Нужно добавить/удалить фазы

**Решение**:
1. Создайте новую версию плана
2. Обновите "История версий" с описанием изменений
3. Пересмотрите зависимости между фазами
4. Обновите "Текущий статус" если нужно

### Непонятно, выполнен ли подпункт

**Проблема**: Критерии завершения неясны

**Решение**:
1. Добавьте конкретные критерии в чеклист фазы
2. Используйте измеримые метрики (coverage, response time)
3. Добавьте примеры ожидаемых артефактов

```markdown
Phase 4: Frontend SPA (6-8 часов)
Phase 5: Integration (3-4 часа)
Phase 6: Testing (4-6 часов)
Phase 7: Deployment (3-4 часа)
```
